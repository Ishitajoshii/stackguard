# Scale measurements

Measured on 13-14 November 2026 on native Windows 11, Intel Core Ultra 5 125H (14 cores / 18 logical processors), Go 1.26.5, with repository/cache/replay data on D:. Hardware and toolchain snapshots are in [lab/ENVIRONMENT.md](lab/ENVIRONMENT.md) and [lab/TOOLCHAIN.md](lab/TOOLCHAIN.md). These are local measurements, not estimates of cloud behavior.

## Real MCP transport

Each row uses 2,000 real calls per mode reading the fetched Go repository README. A server-side barrier proves 1,000 simultaneous handler calls before release; client concurrency alone is not the proof. The driver staggers initial connections by 1 ms to avoid a Windows connection burst, then all 1,000 calls meet the barrier. Separate baseline and proxied server processes use the same workload. Every passing row has zero failures, 2,000 call events and 2,000 separate completion events.

Quantiles use the nearest lower order statistic. Differences subtract separate-run quantiles, not paired request overhead. Barrier wait and startup are included: the noisy/negative differences are **not a demonstrated speedup**. Isolated steady-state overhead needs a longer repeated benchmark. Raw baseline/proxy latencies and original proxy records are alongside each linked summary. Original proxy manifests deliberately show incomplete on Ctrl-C, although the driver verifies all requested responses arrived.

Memory uses Windows GetProcessMemoryInfo peak working set (MiB = 1,048,576 bytes), sampled every 20 ms; the API returns an OS-maintained peak. Peak commit is also recorded. These are probe-process figures, excluding the server, load driver and collector. They are not a total-system memory claim.

Earlier connection bursts produced baseline OS error 10061. Staggered connection initiation fixed those runs while preserving the server barrier. A later proxied attempt had 23 HTTP 502s; increasing reusable upstream idle connections from the default small pool to 2,048 removed that failure in subsequent complete runs. Earlier failed attempts are retained locally under ignored .work/bench-attempts. They are not passing measurements.

After the HTTP disconnect and stdio shutdown fixes, a new [four-worker transport check](results/bench/transport-cancellation-fixes-r2/summary.json) again passed 2,000 requests with 1,000 simultaneous server handlers and matching 2,000 call/2,000 completion records. Peak working set was **121.05 MiB**; Ctrl-C returned 17 in **0.115 s**. Baseline p50/p99 were 363.02/1513.19 ms; proxied 193.98/1437.57 ms. The same separate-run/no-speedup caveat applies. An initial attempt exited before producing the proxied load report; its cause is unresolved and the failed attempt is retained privately. The runner now records a failed driver's exit code and private diagnostics.

## Cancellation and test scope

[Process-level results](results/bench/cancellation-r2/summary.json): scan Ctrl-C 0.072 s, trace 0.051 s, both exit 17 and valid incomplete manifests. These were early interruptions with zero published data records; successful HTTP interruption additionally validates 4,000 already-persisted records. The first cancellation harness attempted to attach before Windows had initialized the console; the runner now waits for the probe's output directory before signalling.

The full Go race suite, vet, four PDF error tests and bounded secret-redaction fuzzing passed locally. Goleak covers proxy and pipeline success/error/cancellation paths. A five-second fuzz command executed 62,304 inputs before its deadline/worker cleanup completed. Algorithm fixtures are labelled as such and are not agent captures.

The stopped large trace **failed** its two-second interrupt budget and was force-terminated by the driver before a manifest appeared. Inspection found part of its multi-gigabyte spill directory already deleted, with four large files remaining: the synchronous cleanup preceded manifest publication. The correction retains interrupted workspaces and records them for later cleanup; scan also now preserves a redacted observation stream before final deduplication. The retained failed-run description is [here](results/bench/large-interruption-failure/summary.json). A passed early cancellation check must not be described as a successful rerun of that late-stage failure. The two older concurrent scans stopped with exit 17 in 0.717 s and 0.172 s; their incomplete runs are not full-corpus results.

The [large-spill regression check](results/bench/late-spill-interruption/summary.json) subsequently passed: actual Ctrl-C after **6,805,070,039 published bytes** and **17,935,283,359 spill bytes** returned **17 in 0.486 s**. Every partial JSONL record was parsed afterward: **9,930,978 events**, exactly matching the incomplete manifest, and zero quarantine records. The manifest recorded the retained workspace. Only after the process had exited and validation finished was that exact derived workspace explicitly removed; the [cleanup record](results/bench/late-spill-interruption/cleanup.json) retains its byte count. The 6.8 GB partial output remains on D:. This is a successful large-interruption regression, not a completed ten-million-event throughput run.

Durability here covers graceful interruption: completed JSONL records use whole-record writes, files are synced on close, and the final manifest is published afterward. Interrupted workspaces are cleanup aids, not resume checkpoints. Power-loss recovery is outside this contract.

All destinations must be new. Keep large replays outside the repository. The pipeline runner records memory and hashes, rejects incomplete runs, and compares worker outputs. The scan/trace and transport drivers now reject either peak working set or peak commit at **512,000,000 bytes** (decimal 512 MB); missing measurements fail too. Display tables use MiB and do not redefine the limit. Older runs used a 512 MiB guard, but their recorded peaks are also below the stricter decimal limit. Queues are bounded to small multiples of workers; external sort chunks are 8 MiB with eight-way merges. More workers need not improve throughput when sorting/disk access is serial or shared.

Use `scripts/collect-pipeline-result.py` to bundle a completed row. Supply `--source` for the matrix directory, a fresh `--out`, the exact `--probe`, `--workers`, `--expected-records` and `--expected-bytes`. It refuses incomplete runs, memory failures, changed measured executable hashes and mismatched counts. It combines all indexed CPU segments with Go pprof, records source-segment checksums, and copies only small results plus CPU/heap profiles. Large event streams and original segments stay on the data drive. The five-segment 100k recording was successfully collected this way; tests also verify that invalid workload sizes and executable identities are rejected before a bundle is created. Run Go tools with the same D: cache/temp environment used for the benchmarks.

`pipeline-check.py --profiles both` is the default and records CPU/heap evidence. Use `--profiles none` for ordinary CLI throughput; the summary explicitly records the mode and the collector does not invent profiles for that run. Retain a separate complete profiled largest-size case. The [100k unprofiled smoke](results/bench/trace-100k-unprofiled/summary.json) completed with the same canonical hashes as the profiled run: 147.896 s, 67,817,472 bytes peak working set and 107,188,224 bytes peak commit. Different competing loads make these timings unsuitable for estimating profiler overhead or claiming a speedup. Both collection modes have been exercised with actual completed runs.

## Profile-guided optimization

New CPU recordings rotate every 30 seconds. The requested `.pprof` path is the first segment; subsequent files append `.part-NNNNNN`, and `<base>.segments.jsonl` lists finalized segments with enclosing wall times. Keep the index and **all** listed files; the first segment alone is not a whole-run profile. Rotation has small unsampled gaps. To aggregate a completed recording in PowerShell:

```powershell
$profileBase = 'D:/path/to/run/cpu-w4.pprof'
$profileParts = Get-Content ($profileBase + '.segments.jsonl') | ForEach-Object {
    Join-Path (Split-Path $profileBase) ($_ | ConvertFrom-Json).file
}
go tool pprof -top @profileParts
```

The runtime soft target and profile windows supplement the existing bounded queues, sort chunks and disk indexes. They do not replace measured process working-set/commit limits. The exact cause of the earlier process-memory peak was not isolated; unbounded CPU-profile metadata and its finalization are now bounded independently of workload length.

The corrected build completed the [identical 100k replay](results/bench/trace-100k-bounded-profiles/summary.json) with unchanged output hashes, 95,617,024 bytes peak working set and 93,671,424 bytes peak commit. All five CPU segments passed framing checks and aggregated successfully with Go pprof. Elapsed time was 124.231 s under overlapping large scans/traces and validation; no speedup is claimed. A separate [actual Ctrl-C check](results/bench/profile-rotation-cancellation/summary.json), after two finalized profile windows and 100,000 published events, returned exit 17 in **0.337 s**. Every partial event and all three finalized profile files validated.

The same corrected build then completed [10,000,000 events / 5,984,000,000 input bytes](results/bench/trace-10m-bounded-profiles-w4/summary.json) with four workers, zero errors, **208,842,752 bytes peak working set** and **249,298,944 bytes peak commit**. All **151 finalized CPU segments** validated and merged successfully with Go pprof; the heap profile also validated. The source revision is `df5c1ee`, with the exact executable hash retained in provenance. Elapsed time was **4,539.736 s** under overlapping workloads, so no isolated speedup is claimed.
